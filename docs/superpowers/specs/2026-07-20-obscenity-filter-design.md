# Site-wide obscenity filter — design

## Purpose

AquaTerra is a platform for 14–19 year-olds. There's currently no profanity/obscenity
filtering anywhere in the app — posts, comments, achievements, profile bios, team
descriptions, and the public contact/collaboration forms all accept and store
arbitrary text with no check. This adds a shared filter used consistently across
every one of those surfaces, including English, Hinglish, and Bengali slang.

## Constraints

- This is a Supabase-direct app with no backend server in the request path
  (`frontend/src/services/api.ts` is explicitly type-only — see CLAUDE.md). All
  existing input validation in the app (CreatePostModal's field checks, etc.) is
  client-side only, so this follows the same pattern for v1.
- Client-side-only means a determined actor bypassing the browser (e.g. hitting the
  Supabase REST API directly) is not stopped by this. That's an accepted, explicit
  tradeoff for v1 — it stops the ~99% case (people typing in the UI) which is the
  actual threat model for accidental/casual profanity from the userbase. A
  server-side backstop (Postgres CHECK/trigger) is a valid future addition but is
  out of scope here to avoid maintaining the word list in two places from day one.
- The actual word list content (words, especially slurs/severe terms) is supplied
  directly by the project owner in chat, not generated by Claude. This doc defines
  the *system* that consumes whatever list is supplied — matching engine, severity
  tiering, normalization, and integration points — not the list itself.

## Architecture

One shared module, no per-surface reimplementation:

```
frontend/src/lib/profanityFilter.ts   — checkText(text) -> FilterResult
frontend/src/lib/profanityWords.json  — the word list (git-tracked, not admin-editable)
```

```ts
type Severity = 'clean' | 'flag' | 'block'
interface FilterResult {
  severity: Severity
  matches: string[]   // which list entries matched, for logging/debugging only —
                       // never surfaced verbatim to the end user in the error message
}
function checkText(text: string): FilterResult
```

Every call site imports `checkText` and reacts to `.severity`. The module owns all
matching logic; call sites only own *what to do* with the result (block a submit
button vs. force `pending_review`).

## Word list format

`profanityWords.json`:
```json
{
  "block": ["...severe/slur-tier words, all languages mixed..."],
  "flag":  ["...milder profanity/slang, all languages mixed..."]
}
```
Flat arrays, no per-language separation needed — matching is language-agnostic once
normalized (see below). Language is only relevant when *supplying* the list, not
when storing or matching it.

## Normalization (evasion handling)

Before matching, run text through:
1. Lowercase
2. Strip whitespace/punctuation *between* letters within a token (catches `w o r d`,
   `w.o.r.d`, `w-o-r-d`)
3. Map common leetspeak substitutions: `4→a 3→e 1→i 0→o 5→s @→a $→s`
4. Collapse runs of 3+ repeated letters to 2 (catches `wooord`, `sooo`)

Matching runs against **both** the raw original text (word-boundary regex, so
`class` doesn't false-positive on a substring match) and the normalized text
(substring match, since normalization already destroyed word boundaries). A hit on
either counts.

False positives are handled by keeping the block message generic ("this contains
language that isn't allowed here") rather than quoting the matched word back — less
accusatory when normalization produces a false hit, and doesn't teach evasion by
revealing exactly what triggered it.

## Enforcement per tier

| Tier | Posts / Comments / Achievements | Contact / Collaboration forms |
|---|---|---|
| `block` | Submit disabled, inline error, nothing reaches the DB | Submit disabled, inline error |
| `flag`  | Submission proceeds but forces `status = 'pending_review'` — even for HoDs/directors, who currently auto-publish | Submit disabled, inline error (same as block — no moderation queue exists for these forms, so there's nothing to "softly" route into) |

The `flag`→`pending_review` behavior reuses the *existing* moderation queue
(`director/PostModeration.tsx`) as-is — a flagged post just appears in Post Queue
like any other pending post. No new desk UI.

## Call sites (6)

Each just calls `checkText()` on submit and branches on `.severity`:

1. `feed/CreatePostModal.tsx` — body + title, all three post modes (normal/job/blog)
2. Comment composer (wherever comments are submitted — `PostFocusModal.tsx` /
   `PostPage.tsx` / `FeedPostCard.tsx`'s inline comment sheet)
3. `profile/AddAchievementModal.tsx` + `profile/EditAchievementModal.tsx` — title + description
4. `profile/EditProfilePage.tsx` — bio field
5. `director/TeamManagement.tsx` — team name + description (create/edit)
6. `public/ContactPage.tsx` + `public/CollaborationsPage.tsx` — their inquiry forms

## Testing

- Unit tests for `checkText()`: clean text, exact block match, exact flag match,
  spaced-evasion match, leetspeak-evasion match, word-boundary false-positive
  avoidance (a word containing a shorter blocked substring should NOT match unless
  it's an exact token).
- Manual verification per call site: attempt a `block`-tier submit (confirm
  disabled + error, nothing persisted) and a `flag`-tier submit on a post (confirm
  it saves as `pending_review` even when submitted by a super-admin dev-preview
  session, then appears in Post Queue).

## Out of scope (v1)

- Server-side/DB-level enforcement (noted above as a constraint, not forgotten)
- Desk-editable word list UI (explicitly deferred — code/config file only)
- Per-language list separation or language detection
- Blog `body`/`content` fields specifically (blogs are CMS-authored by leaders
  directly, not through a moderation-relevant public-submission surface — can be
  added to the call-site list later with zero changes to the shared module if
  that changes)
