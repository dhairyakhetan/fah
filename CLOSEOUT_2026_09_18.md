## 2. Found live, ranked

### P0. `authenticated` holds a table-level SELECT grant on `members`

**Measured.** `pg_class.relacl` on `public.members` reads `authenticated=rdDxtm/postgres`. The leading `r` is SELECT on every column. Column grants add to a table grant, they never cap it, so the entire column-by-column PII design is void.

Combined with `members_select` (`status = 'active' OR is_director() OR auth_uid = auth.uid()`), any authenticated session can run `GET /rest/v1/members?select=email,phone,full_name` and get the roster.

| Exposed to any signed-in account | Count |
|---|---|
| Active member rows | 1,327 |
| Email addresses | 1,327 |
| Phone numbers | 58 |
| `auth_uid` values | 65 |
| Of those, giving a school class as their cohort | 839 |

"Any signed-in account" includes a brand-new `pending_approval` row, which anyone with a Google login creates in one click. No approval needed.

**Cause:** `frontend/scripts/member_appeal_after_removal_2026_09_14.sql:19`

```sql
grant select on public.members to authenticated;
```

The migration added the `previously_removed` column, correctly noted in its own comment that a new `members` column starts with zero privileges, and then wrote the grant without a column list. `grant select (previously_removed) on ...` became `grant select on ...`. One missing parenthesised name, four days live.

This is the third time the `members` grant model has caused an incident here and the first time the failure was a grant that was too **wide** rather than one that was missing. The existing lore in CLAUDE.md warns only about the missing direction.

**Fix:** section 1 of the migration. Verified safe before writing it: no code anywhere selects `members.email` or `members.phone` directly (the only two matches are comments saying not to), there is no `select('*')` on members anywhere in `src/`, own-row reads go through the `get_own_member()` SECURITY DEFINER RPC, and all 40 columns were checked individually against `pg_attribute.attacl` so the revoke leaves every legitimate column exactly as it was.

### P0. 2,357 event photographs are downloadable by anyone with the anon key

**Proven, not inferred.** Using only the publishable anon key that ships in the public JavaScript bundle:

```
POST /storage/v1/object/list/photobooth-raw-photos        -> 200, folder listing
POST /storage/v1/object/list/photobooth-raw-photos/<dir>  -> 200, file listing
GET  /storage/v1/object/photobooth-raw-photos/<dir>/<f>   -> 200, 112,713 bytes, image/jpeg
```

A real photograph, downloaded unauthenticated, on 2026-09-18.

| Bucket | Objects | Size | `public` flag |
|---|---|---|---|
| `photobooth-raw-photos` | 1,831 | 217 MB | false |
| `photobooth-print-sheets` | 522 | 40 MB | false |
| `photobooth-assets` | 4 | 70 kB | true |

Five policies on `storage.objects` grant `anon` read, insert, update or ALL on these, with the bucket name as the only predicate.

**Why nobody noticed:** two of the three buckets are flagged `public: false`, so the dashboard presents them as private while the RLS policy hands `anon` full access anyway. The flag and the policy disagree, and the policy is the one that decides.

**The feature is gone.** `grep -rl photobooth frontend/src` returns nothing. No component, service or route references any of these buckets. Newest object is 2026-08-22.

AquaTerra's members are overwhelmingly school students, so assume the subjects are minors. Section 5 of the migration closes the access and **keeps every file**, because deleting 2,357 photographs is your decision, not a security fix. Once it runs they are reachable only with the service key, which is what the dashboard uses.

My recommendation, separately from the migration: delete them. They are photographs of children in an object store with no retention date, attached to a feature that no longer exists.

### P1. `post_feed_view` serves unmoderated posts to anonymous clients

`post_feed_view` is SECURITY DEFINER, so it runs as `postgres` and **RLS on `posts` does not apply to it at all**. Its own WHERE clause filters `deleted_at IS NULL` and says nothing about status. `anon` holds SELECT on it.

Result, measured: **14 posts with `status = 'pending_review'`** readable by anyone with the anon key. Member submissions that no moderator approved.

No scheduled posts exist today, so there is no embargo leak this minute. The same hole would leak every scheduled announcement the day one is created, which is the larger forward risk.

**I rejected the obvious one-line fix.** Flipping the view to `security_invoker = true` makes RLS apply and closes the leak in one line. But the view INNER JOINs `members` for the author, and `members_select` only exposes `status = 'active'` rows, so the moment any member is archived or leaves, **every post they ever authored would silently vanish from the public feed**. Today that hides nothing (all 584 published posts have an active author, measured), which is exactly what makes it a trap: it passes every check now and deletes history later. Content disappearing without an error is this codebase's most repeated bug.

Section 3 puts the predicate in the view instead, mirroring `posts_select` exactly. It rewrites the view from the database's own `pg_get_viewdef` output rather than a transcription, and refuses to run if the stored definition is not shaped the way it expects.

### P1. Anyone can delete or replace every project image

Three policies on `storage.objects` (`Anon write`, `Anon update`, `Anon delete` for `project-images`) have an **empty role list**, which in Postgres means PUBLIC. The only predicate is the bucket name. No ownership check, no role check.

24 objects, 23 MB, every welfare project image on the public site. A stranger with the anon key can replace any of them with anything, or delete all 24.

This settles the long-open question about `project_images_bucket_tighten_2026_08.sql`, which said "do not apply blind" and carried no applied marker. **It was never applied.** Section 4 applies it, rewritten to be idempotent, gated on `is_director() OR is_super_admin()` so the director desk keeps working. Public read is deliberately left open.

### P2, in the migration

- `pending_member_approvals` is granted to `anon`. It returns zero rows because of its inline guard, so it is not a live leak, but the grant has no reason to exist.
- `member_directory_view` has no `security_barrier` while its sibling `rejected_member_approvals` does. Hardening, no observed leak.

### P2, recorded and deliberately not changed

`anon` and `authenticated` hold table-level DELETE on `members`. It is inert: the only DELETE policy is `Super admin can delete members` USING `is_super_admin()`, and RLS is evaluated regardless of the grant. Tidying it risks breaking a super-admin path for no measured gain.

## 3. What the database got right

A review that lists only faults misrepresents this database. Measured, not assumed:

- **RLS is enabled on all 56 public tables, and every one has at least one policy.** No exceptions, no gaps.
- **Performance advisors are nearly clean:** one unindexed foreign key (`members_deleted_by`, low traffic), 39 unused indexes (mostly recently created, so "unused" is expected). No `auth_rls_initplan` findings and no multiple-permissive-policy findings, which means the RLS is written efficiently rather than merely correctly.
- **The three SECURITY DEFINER views the advisor flags as ERROR are mostly correct.** `member_directory_view` and `rejected_member_approvals` both carry `WHERE is_director() OR is_super_admin()` inline, and `member_directory_view` further gates `phone` on `is_super_admin()`. Only `post_feed_view` is a real problem. The advisor cannot tell the difference; do not "fix" the other two.
- **`pending_post_reviews` is safe precisely because it IS `security_invoker`**, so RLS applies. The correct setting genuinely differs per view, which is why the lint is a poor guide here.
- **Every one of the 40 `members` column ACLs is individually correct.** Only the table-level grant on top of them is wrong.
- **`sim_seed_registry` is empty.** No `[SIM]` rows in production, so every count in this document is real data. That caveat can be dropped from future reports.
- **`log_action()` remains the best-designed guardrail in the system.** 27,658 rows, member identity stamped server-side, unforgeable.

### The one error class still happening

Everything else resolved by 2026-09-11. What remains is stale-chunk failures, 3 to 13 a day, roughly one per session.

These are normal for an SPA that deploys often, and `lazyWithRetry` recovers users by forcing a reload. But there is a config defect making them worse, confirmed live:

```
GET /assets/NotFoundPage-BmsaCBV3.js   (a stale hash)
-> HTTP 200, Content-Type: text/html
```

The catch-all rewrite `/(.*) -> /` swallows missing assets and serves the homepage HTML instead of a 404. So `lazyWithRetry`'s retry **can never succeed**: the second attempt fetches the same HTML. Only the reload fixes it, and the error is logged as the misleading "Failed to fetch dynamically imported module". `nosniff` is set, so the browser correctly refuses to execute it.

**Suggested fix, not applied:**

```json
{ "source": "/((?!assets/|fonts/).*)", "destination": "/" }
```

I deliberately did not make this change. CLAUDE.md documents the catch-all rewrite as the single most dangerous line in the config, `verify-routing.mjs` gates it, and it cannot be verified until a deploy. Shipping it unverified alongside 80 already-uncommitted files is the wrong trade. Do it as its own change, alone, and watch the smoke test.
