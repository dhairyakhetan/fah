## ✅ Applied and verified live

### DB · `restore_members_pii_column_lockdown`
The critical one ([[Simulation Log 2026-08-10]] SIM-1). `authenticated` held
**table-level** SELECT on `members`, which is why the column-level grants in
`members_pii_lockdown_2026_07_29.sql` had no effect — a column GRANT cannot
restrict anything while a table GRANT exists.

```sql
REVOKE SELECT ON public.members FROM authenticated;
-- then GRANT SELECT (every column except email, phone, auth_uid, google_id)
```

The safe column list is derived from `information_schema` inside a `DO` block, so
a future column is not silently dropped from the grant.

**Verified:**

| Check | Before | After |
|---|---|---|
| `select count(email) from members` as `authenticated` | **1314** | `ERROR 42501: permission denied` |
| `select count(phone) …` | **37** | blocked |
| rows visible (`count(*)`) | 1314 | 1314 — unchanged |
| MembersPage column shape | ok | ok |
| `member_directory_view` email read (leader path) | ok | ok |
| `get_own_member()` / `ensure_member()` / `create_notification()` EXECUTE | ok | ok |

**Regression-checked in the browser** against this same database: `/` renders 584
posts, `/members` renders 1314 members, `/login` renders — no console errors on
any of them.

> [!note] Why this was safe to apply immediately
> The application was **already fully written for the locked-down state** —
> `AuthContext.fetchMember` uses the `get_own_member()` RPC,
> `profileService.updateProfile` and `RegisterPage` deliberately omit `.select()`
> after UPDATE, and `directorService` reads emails through `member_directory_view`.
> Every one of those has a comment citing the lockdown migration. The code shipped;
> the grant change did not.

### Two new bugs found while writing these

**`approve_post_category(uuid, text)` is broken, not just duplicated.** It
references `posts.pending_categories` — **a column that does not exist** — so it
raises at runtime. The `(uuid, varchar) → json` overload is the real
implementation. PostgREST resolves by argument type and the client sends a
string, which is very likely why `post_approvals` has **0 rows** despite the
feature being wired end to end. My earlier note guessed to keep the `text` one;
that was wrong, and the file drops it instead.

**`create_notification()` matched `members.uuid = auth.uid()`** for its `'lead'`
branch. `members.uuid` is not `auth.users.id` — the correct column is `auth_uid`.
So the branch could never grant, and team leads could not send
`post_approved` / `team_invite` / `team_join_accepted`. Same uuid confusion as the
dormant arcade policies (C6).

### Still needs a small follow-up
A `SECURITY DEFINER` counter for **onboarded members** (`status='active' AND
auth_uid IS NOT NULL`). Filtering on `auth_uid` requires column SELECT, which is
now correctly revoked — so the honest "41 real users" number needs a definer
